# Code Review 评审清单

## 评审前置

先读 PR 描述，搞清三件事：**要解决什么问题**、**改了哪些文件**、**作者自测了什么**。

看不懂意图就直接问，不要基于猜测评审——猜错的评审意见比不评审更浪费时间。

## 七维度清单

### 1. 正确性（最高优先级）

- [ ] 逻辑与需求描述一致
- [ ] 循环边界正确（`<` vs `<=`，off-by-one）
- [ ] 空值/空数组/空字符串处理
- [ ] 并发场景有竞态保护
- [ ] 返回值与调用方预期匹配
- [ ] 错误分支真的处理了，不是只 `catch` 了不做事

### 2. 边界与异常

- [ ] 参数校验：类型、范围、必填
- [ ] 外部输入（用户输入、API 响应、文件内容）不可信
- [ ] 超时、重试、降级策略
- [ ] 资源释放（文件句柄、连接、锁）
- [ ] 大输入不炸内存（分页/流式）

### 3. 可读性

- [ ] 命名说得清用途（`data`、`temp`、`handle` 这类名字要问）
- [ ] 函数单一职责，不是「顺便也做了」
- [ ] 嵌套层级 ≤ 3，超过就该抽函数
- [ ] 魔法数字有常量名
- [ ] 注释解释**为什么**，不复述代码

### 4. 耦合与设计

- [ ] 模块边界清晰，没有跨层直调
- [ ] 依赖注入而非硬编码
- [ ] 修改一处不需要连带改五处
- [ ] 没有为「将来可能用到」提前抽象
- [ ] 没有复制粘贴大段逻辑（该抽公共函数）

### 5. 健壮性

- [ ] 日志有上下文（谁、什么参数、什么结果），不是裸 `print("error")`
- [ ] 日志不泄露敏感信息（密码、token、身份证）
- [ ] 幂等性（重试不会重复扣款/重复插入）
- [ ] 事务边界正确

### 6. 规范一致性

- [ ] 与项目现有代码风格一致
- [ ] Commit 信息符合 Conventional Commits
- [ ] 没有无关改动混入（格式化整文件、删无用 import 应单独提交）
- [ ] 依赖新增有理由，不是随手加

### 7. 安全

- [ ] SQL 参数化，无字符串拼接
- [ ] 输出转义，防 XSS
- [ ] 权限校验在每个入口，不靠前端隐藏
- [ ] 无硬编码密钥/证书
- [ ] 文件上传有类型和大小限制
- [ ] 反序列化不信任外部数据

## 意见写法

**烂写法** → **好写法**：

| 烂 | 好 |
|---|---|
| 「这里不太好」 | 「第 42 行 `items[0]` 在空数组时抛异常，建议先判 `items.length > 0`」 |
| 「性能有问题」 | 「第 88 行在 for 循环里查数据库，N+1 查询。建议先批量查出来再 map」 |
| 「建议重构」 | 「这段 60 行的函数承担了校验+转换+落库三件事，建议拆成 `validate` / `transform` / `persist`」 |
| 「加个注释」 | 「第 15 行的位运算 `x >> 3` 含义不明，建议注释说明是除以 8 取整」 |

每条意见标注严重程度：

- **[必须改]** 正确性/安全问题，不改不能合
- **[建议改]** 可维护性问题，作者可判断
- **[可选]** 风格偏好，作者有权不采纳

**区分「必须改」和「我偏好」**。把自己的口味当规范要求，是 CR 最常见的坏毛病。

## 评审心态

**见贤思齐，见不贤而内自省**——评审别人代码时，顺手检查自己有没有同样的毛病。CR 不是找茬比赛，是把缺陷挡在合并之前。

三条底线：

1. 对事不对人。「这个实现有问题」不是「你有问题」
2. 提出问题的同时给方向，不做只会挑刺的评审
3. 自己不确定的地方标「疑问」而非「错误」，别装懂
