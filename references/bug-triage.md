# 缺陷工单管理规范

## 分级标准

| 级别 | 定义 | 响应要求 | 合入 main |
|---|---|---|---|
| **P0** | 阻断核心流程、线上故障、数据损坏/丢失、安全漏洞 | 立即修复，其他工作让路 | **禁止**，必须修复 |
| **P1** | 主要功能异常，影响核心使用，无绕过方案 | 本迭代必修 | **禁止**，需特殊放行说明 |
| **P2** | 次要功能异常、交互瑕疵，有绕过方案 | 排入后续迭代 | 允许 |
| **P3** | 优化建议、体验小问题、文案错误 | 有空再修 | 允许 |

判断口诀：**能不能用 → 能不能绕过 → 影响多少人**。

- 完全不能用 → P0
- 能用但核心功能坏了、绕不过 → P1
- 能用、有绕过方案 → P2
- 用得挺好，只是不够好 → P3

## 状态流转

```
         ┌──────────────────────────────────┐
         ↓                                  │
      新建 → 修复中 → 自测通过 → CR验证 → 关闭
         ↑                        │
         └────── 重开 ←───────────┘  (回归失败)
```

| 状态 | 含义 | 谁推动 |
|---|---|---|
| 新建 | 已登记，未开始修 | 发现者 |
| 修复中 | 开发在改 | 开发 |
| 自测通过 | 开发自测过了，待评审 | 开发 |
| CR验证 | 评审/测试在验证 | 评审者 |
| 关闭 | 验证通过 | 评审者 |
| 重开 | 回归失败，问题复现 | 验证者 |

**规则**：只有验证者能置「关闭」，开发不能自己关自己的 bug。这是防止「假修复」的唯一有效机制。

## 必须记录的字段

| 字段 | 说明 | 何时填 |
|---|---|---|
| 单号 | BUG-0001 递增，脚本自动生成 | 创建时 |
| 标题 | 一句话说清「什么场景下什么坏了」 | 创建时 |
| 优先级 | P0-P3 | 创建时 |
| 状态 | 见上表 | 持续更新 |
| 复现步骤 | 能让别人重现的最小步骤 | 创建时 |
| 期望行为 | 正确的结果应该是什么 | 创建时 |
| 关联 PR/版本 | 哪个改动引入/修复的 | 修复时 |
| 根因 | 需求/设计/编码/测试 | **关闭时必填** |

复现步骤写得烂的 bug 等于没提。「点了按钮报错」→ 应该是「Chrome 120，空购物车页面点『结算』，控制台报 TypeError: cart.items is undefined」。

## 命令速查

```bash
# 新建
python scripts/bug_ledger.py add --title "空购物车点结算崩溃" --priority P1 \
  --repro "1.清空购物车 2.点结算" --expected "提示购物车为空" --related-pr "PR-42"

# 列表（只看未关闭）
python scripts/bug_ledger.py list --open-only

# 按优先级
python scripts/bug_ledger.py list --priority P0

# 改状态
python scripts/bug_ledger.py update BUG-0001 --status 修复中 --note "已定位到空数组判断缺失"

# 关闭（必须补根因）
python scripts/bug_ledger.py update BUG-0001 --status 关闭 --root-cause 编码疏漏

# 门禁校验（返回非0表示有未关闭 P0/P1）
python scripts/bug_ledger.py stats

# 导出 markdown 表格
python scripts/bug_ledger.py export --out bug-report.md
```

## 台账表格样式（交付物中展示）

| 单号 | 标题 | 优先级 | 状态 | 关联PR/版本 | 根因 |
|---|---|---|---|---|---|
| BUG-0001 | 空购物车点结算崩溃 | P1 | 关闭 | PR-42 / v1.2.0 | 编码疏漏 |
| BUG-0002 | 金额千分位未处理 | P2 | 新建 | - | 未定 |

## 根因归类

复盘时每条缺陷必须归一类，这决定改进措施往哪使：

| 根因 | 特征 | 改进方向 |
|---|---|---|
| **需求问题** | 做出来不是用户要的 | 需求澄清加验收标准 |
| **设计问题** | 架构撑不住场景 | 方案评审加边界推演 |
| **编码疏漏** | 逻辑写错、漏判空 | 加强参数校验 + 单测 |
| **测试漏测** | 场景没覆盖到 | 补测试用例，边界优先 |

统计规律：**根因分布决定流程该改哪一环**。编码疏漏占大头 → 补单测；需求问题占大头 → 补需求评审。别笼统说「加强管理」。

## 反模式

- 开发自己关自己的 bug
- 优先级全填 P1（等于没有优先级）
- 缺陷只在聊天里说，不进台账（下次一定忘）
- 关闭不填根因（复盘时无据可查）
- 修完不更新状态（台账变成历史垃圾）
- 一个 bug 单塞多个不相关问题
